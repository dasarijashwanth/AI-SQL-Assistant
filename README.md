# AI SQL Assistant

Ask questions about an e-commerce database in plain English, get back the
SQL that ran, the rows it returned, and a one-line summary. Built with
LangChain v1 (`langchain.agents.create_agent`) and the SQLDatabaseToolkit,
served by FastAPI, and designed from day one to be **read-only by
construction**: the agent can look, but it cannot touch.

## Why this project

Text-to-SQL demos usually stop at "the model wrote a query." The
interesting engineering is everything around that moment: proving the
query cannot write, capping how much it can return, showing the exact SQL
that executed, and measuring whether the answers are actually right. This
project builds that whole frame, then points it at a deterministic demo
database anyone can regenerate.

## Features

- Natural-language questions answered by an agent with SQL tools
  (list tables, read schema, sample rows, distinct values, check
  query, run query), all under a per-query timeout.
- Every response shows the executed SQL, the result rows, the row count,
  and a one-line plain-English explanation.
- A deterministic synthetic e-commerce database (SQLite): customers,
  products, orders, order_items, payments, reviews.
- An eval harness over 25 questions (`evals/questions_day3.json`,
  scored by `app/eval.py`, results in `evals/results_day3.md`):
  20 agent questions across lookups, filters, joins, aggregations,
  and ordering/limits, plus 5 adversarial items aimed at the safety
  layers. Day 3 score: 25/25, average agent latency 46.2 ms.
- Runs fully offline with no API key (see "Offline mode" below), and
  uses a real OpenAI model when a key is present.

## Safety model (the day 1 story)

Read-only is enforced in three independent layers, so no single bug
opens a write path:

1. **Query guard** (`app/guard.py`): every SQL string, from the agent or
   from the API, passes `validate_select()` before execution. Only a
   single SELECT (or WITH ... SELECT) is allowed. Write keywords
   (INSERT, UPDATE, DELETE, DROP, ALTER, PRAGMA, CREATE, and friends)
   are rejected anywhere in the statement, multi-statement input is
   rejected, and a LIMIT no larger than the row cap (default 200,
   `SQL_ASSISTANT_ROW_LIMIT`) is enforced. String literals are stripped
   before keyword scanning, so a product named "Delete Pro" does not
   trip the alarm.
2. **Checker swap** (`app/tools.py`): the toolkit's `sql_db_query_checker`
   tool is replaced by the guard itself, so the "check" step is a real
   policy check, not the LLM grading its own homework. The
   `sql_db_query` tool is wrapped so every executed statement is
   validated again and captured for the API response.
3. **Read-only connection** (`app/db.py`): the SQLAlchemy engine opens
   SQLite with URI `mode=ro` and sets `PRAGMA query_only = ON` on every
   connection. Even a hypothetical guard bypass hits a connection that
   physically cannot write.

## Architecture

```
question
  -> FastAPI POST /ask            (app/main.py)
  -> create_agent                 (app/agent_service.py)
       model: ChatOpenAI, or FakeSQLChatModel when offline
       tools: SQLDatabaseToolkit, with guard checker + guarded query
  -> agent loop: list tables -> schema -> check query -> run query
  -> guard validates every statement        (app/guard.py)
  -> read-only SQLite engine                (app/db.py)
  -> response: {question, sql, rows, row_count, explanation}
```

The demo database is generated by `scripts/build_demo_db.py` from a
fixed seed (`random.Random(42)`), so its content is reproducible:
40 customers, 25 products, 120 orders across Oct 2025 to Sep 2026,
with matching order items, payments, and reviews.

## Offline mode (no API key needed)

If `OPENAI_API_KEY` is not set, the app swaps in `FakeSQLChatModel`
(`app/fake_llm.py`): a small deterministic chat model that drives the
same agent loop (list tables, schema, check, query) and issues canned
SQL for the demo questions via a keyword map. The agent, tools, guard,
and database are all real; only the language model is stubbed. The
entire test suite runs in this mode. Set the key and the same code path
uses `ChatOpenAI` with the model from `SQL_ASSISTANT_MODEL`
(default `gpt-4o-mini`).

## Setup

### macOS / Linux

```bash
cd week-04-sql-assistant
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python scripts/build_demo_db.py
python -m uvicorn app.main:app --reload
```

### Windows (PowerShell)

```powershell
cd week-04-sql-assistant
py -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python scripts/build_demo_db.py
python -m uvicorn app.main:app --reload
```

Optional, to use a real model instead of the offline fake:

```bash
export OPENAI_API_KEY=sk-...            # PowerShell: $env:OPENAI_API_KEY = "sk-..."
export SQL_ASSISTANT_MODEL=gpt-4o-mini  # optional, this is the default
```

Configuration is environment-driven (`app/config.py`):
`SQL_ASSISTANT_DB_PATH` (default `data/demo.db`),
`SQL_ASSISTANT_MODEL` (default `gpt-4o-mini`),
`SQL_ASSISTANT_ROW_LIMIT` (default 200),
`SQL_ASSISTANT_QUERY_TIMEOUT` (default 10 seconds).

## Usage

Health and active LLM mode:

```bash
curl http://localhost:8000/health
# {"status":"ok","llm":"fake","model":"fake-offline"}
```

Ask a question:

```bash
curl -X POST http://localhost:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "What are the top 5 products by units sold?"}'
```

```json
{
  "question": "What are the top 5 products by units sold?",
  "sql": "SELECT p.name AS product, SUM(oi.quantity) AS units_sold FROM order_items oi JOIN products p ON p.id = oi.product_id JOIN orders o ON o.id = oi.order_id WHERE o.status != 'cancelled' GROUP BY p.name ORDER BY units_sold DESC LIMIT 5",
  "rows": [{"product": "Robot Vacuum", "units_sold": 58}],
  "row_count": 5,
  "explanation": "Query executed. Result: ..."
}
```

Run a guarded SELECT directly (transparency and debugging):

```bash
curl -X POST http://localhost:8000/query \
  -H "Content-Type: application/json" \
  -d '{"sql": "SELECT COUNT(*) AS n FROM orders"}'
# {"sql":"... LIMIT 200","rows":[{"n":120}],"row_count":1}

curl -X POST http://localhost:8000/query \
  -H "Content-Type: application/json" \
  -d '{"sql": "DELETE FROM orders"}'
# 400: Only SELECT statements are allowed (got DELETE).
```

Inspect the schema:

```bash
curl http://localhost:8000/schema
```

## Tests

```bash
python -m pytest -q
```

38 tests, all offline: guard rejections (DELETE, DROP, UPDATE, INSERT,
multi-statement), LIMIT enforcement and clamping, schema loading,
`/ask` answering the three wired demo questions (total revenue, top 5
products by units, orders per month) with real rows, `/query`
executing a valid SELECT while rejecting writes with a 400, the Day 2
exploration tools (sample rows, distinct values, injection names
rejected as unknown tables/columns), query timeouts (a runaway
recursive CTE aborts with a 504 and the engine recovers), the
stricter system prompt, and the Day 3 eval harness itself (scoring
logic, fake-model routing per question family, adversarial
rejections, end-to-end subset run).

## Eval plan

`evals/demo_questions.json` holds 10 questions, each with a reference
SQL query and a machine-checkable expectation (non-empty result,
minimum row count, or a positive scalar). Day 3 built the scored
harness on top of that pattern: `evals/questions_day3.json` holds 25
questions (20 agent, 5 adversarial), `app/eval.py` scores them, and
`scripts/run_eval.py` runs the set and writes
`evals/results_day3.md`. Day 3 score: 25/25 (agent 20/20,
adversarial 5/5), average agent latency 46.2 ms, orders row count
unchanged at 120 before and after the adversarial batch.

Honest scope note: in offline fake-LLM mode the harness measures
pipeline correctness (the keyword-mapped stand-in routes each question
family to a sensible query, the guard lets it through, the database
answers it), not open-ended model reasoning. With a real model behind
the same code path, the same harness and checks apply unchanged.

  read-only guard in three layers, deterministic demo DB, offline fake
  model, 17 tests, 10-question eval set.
- **Day 2 (done):** Agent hardening: sample-rows and distinct-value
  lookup tools, stricter system prompts, query timeouts, better error
  messages. All three Day 1 safety layers intact and still enforced
  on every execution path.

  reporting: 25/25 (agent 20/20, adversarial 5/5), average agent

  Fake-model keyword map extended with one branch per new question
  family; the three Day 1 wired questions keep their original
  mapping. 38 tests.
